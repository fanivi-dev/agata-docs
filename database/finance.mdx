## Model (simplified)

```txt
finance_accounts ──< finance_transactions >── profile_tags (domain_scope=finance)
        │                      │
        │                      ├── finance_recurring_rules (+ profile_tag_links)
        │                      ├── finance_debts (group_id → debt_groups)
        │                      └── finance_savings_goals
        └── net worth / balances in cents
```

Finance-specific categories (`finance_categories`) were removed. Classification = profile **tags** with `domain_scope = 'finance'` (finance pickers also include `general` tags).

## Catalog

### Finance tags

Uses `profile_tags` (`domain_scope = 'finance'`) and, for recurring rules, `profile_tag_links` (`entity_type = finance_recurring_rule`). CRUD via the tags API, not finance. Legacy entity types (`transaction`, `recurring_rule`) are normalized to `finance_transaction` / `finance_recurring_rule`.

## Recurring

### `finance_recurring_rules`

| Column | Notes |
| --- | --- |
| `type` | expense \| income \| transfer |
| `amount_cents` / `day_of_month` | |
| `from_account_id` / `to_account_id` / `debt_id` / `savings_goal_id` | Transfer requires distinct origin and destination; does not allow debt or savings. Income may link a savings goal (000064). |
| agenda/email reminders | several `*_reminder_*` fields |
| `max_occurrences` / `generated_occurrence_count` | |
| `effective_start_year` / `month` | |
| `is_active` / soft delete | |

Rule tag: `profile_tag_links` (no column on the rule).
Recurring transfers do not allow a tag and, when materialized, generate a
pending `transfer` transaction. The user marks it paid when
appropriate; only then do they move balance between accounts. They do not alter the
profile's projected income, expense, or net.

### `finance_recurring_ensure_cooldown`

Control of “ensure month” per profile+year+month. `EnsureRecurringForMonth` **reads** `last_run_at` (TTL ~10 min) before materializing; responds `{ skipped }` if it does not run.

### `finance_debt_payments`

Payment linked to `debt_id`. Registering a payment creates a paid `expense` and stores its `transaction_id`. Creating or marking as paid any `expense` with a debt syncs this row and the debt balance in the same transaction; reverting to pending or deleting it reverses the effect. Migration 000037 repairs current recurring occurrences that did not inherit the debt and recovers paid movements that had no payment row.

**Indexes:** `(debt_id, occurred_at DESC)` (000036) for history and partial unique `(profile_id, transaction_id)` (000037) so each movement originates at most one payment.

### `finance_savings_goals`

`target_amount_cents`, `current_amount_cents`, `target_date`, `account_id` → accounts (000035; default destination for contributions), `currency` (000064; backfilled from the linked or primary account).

### `finance_savings_contributions`

Contributions with `amount_cents`. Creating or marking paid an `income` with `savings_goal_id` syncs this row and the goal balance in the same transaction. Partial unique `(profile_id, transaction_id)` (000064) so each movement originates at most one contribution. Direct contribution create still writes a paid income when `transaction_id` is omitted.

## Plan limits

Finance accounts and transactions are unlimited for customers. Private abuse safeguards may return `CAPACITY_GUARD_REACHED`. Tags share the general `profile_tags` safeguard (not a separate category quota).
