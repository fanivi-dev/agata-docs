## Model

1. The user authenticates in **Next.js** with **Better Auth**.
2. Server actions / route handlers validate the session (`requireBetterAuthSession`).
3. The call to Go carries **internal headers** with user identity (and profile context depending on the endpoint).
4. Go applies **access control** (membership, roles, enabled apps).

Better Auth has **its own tables** (`user`, `session`, `account`…) distinct from platform `users`. The typical link is `users.auth_user_id` → Better Auth id.

See [Database → Better Auth](/database/better-auth) and [General → Auth](/platform/auth).

## Access

Access logic in `internal/platform/access/` (and checks in application services).

Profile roles (check in schema): `owner`, `admin`, `member`.

## What not to do

- Expose the Go API without the app session path (in production environments).
- Trust only `profileId` from the body without verifying membership.
