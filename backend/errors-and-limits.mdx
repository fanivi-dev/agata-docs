## Application errors

Shared: `internal/shared/apperrors/`.

On the client they are mapped with `isStructuredApiErr` / `AppError` in `apps/app/shared/utils/error-handler.ts`.

## Plan limits

Stable customer-facing keys (API + i18n):

- `members_per_profile`
- `profiles_per_owner`
- `agent_credits_per_month`

Key definition: `apps/app/shared/utils/plan-limits/keys.ts`.

Product plans (Free / Pro / Business): see [Billing and plans](/platform/billing-plans).

Content resources use private abuse safeguards rather than plan-limit errors. When one is reached, the API returns `CAPACITY_GUARD_REACHED` with a neutral message and no limit, counter, or plan metadata. The handler records the internal key, effective tier, usage, and safeguard value in structured server logs.

## Profile counters

The `profiles` table keeps denormalized counters (`member_count`, `project_count`, …) and billing fields. Detail in [DB → Platform](/database/platform).

### Usage cache (Upstash)

The limiter’s `Assert*Cap` checks share a private snapshot in Upstash:

- Key: `profile:usage:{profileId}`
- TTL: 5 minutes
- Payload: plan + used (members, projects, tasks, tags, activities, reminders, finance accounts/transactions, goals)
- Miss or Upstash disabled → load from Postgres (one multi-count SQL) and write the cache
- Invalidation on creates/deletes/invites and when syncing the billing plan

Customer-facing capacity is derived with `EntitlementsFor(plan)`. Private safeguards are derived with `AbuseLimitsFor(plan)`; the cache does not store either set of integers.
